## 3. The Durable Object (Q3)

- A plain (non-Effect) Worker declares a Durable Object as a `Cloudflare.DurableObject<Shape>(className, props?)` value under the Worker's `env` prop. The `env` key is the binding name, and `className` defaults to the first argument. For this app that is `env: { TRIP_STORE: Cloudflare.DurableObject<TripStore>("TripStore") }`. There is no separate `exports` or `migrations` input. The `exports` prop on `WorkerProps` is `@internal` and serves Effect-native Workers. **[V]** — `alchemy@b83 src/Cloudflare/Workers/DurableObject.ts:211-217`, `:991-1012`; `src/Cloudflare/Workers/Worker.ts:761-792`. (Some JSDoc examples in `DurableObject.ts` still write `bindings:`; `WorkerProps` has no such field.)
- Since `beta.82`, v2 deploys Durable Objects through Cloudflare's declarative `exports` map on the script upload. It builds the metadata object with `exports: nonEmptyExports(exportsMap)` and no `migrations` key. **[V]** — `alchemy@b83 src/Cloudflare/Workers/WorkerProvider.ts:3770-3819` (the `exports` field is `:3812`)
- The legacy `migrations` object remains only on the Worker Previews path (`preview.of`), which this app would not use. **[V]** — `alchemy@b83 src/Cloudflare/Workers/WorkerProvider.ts:3151-3212`
- The `exports` path landed in PR #2135 (commit `74beb7f`, merged 2026-10-09) and first shipped in `beta.82` on 2026-10-12. Before it, Alchemy could not deploy to a Worker like this one. Issue #2072 reports `BadRequest: This Worker was last deployed using the declarative exports flow; reverting to migrations is not supported`. **[V]** — https://github.com/alchemy-run/alchemy/pull/2135; https://github.com/alchemy-run/alchemy/issues/2072 (closed 2026-10-09); `gh release view v2.0.0-beta.82`
- v1 (`0.94.0`) always sends a legacy `migrations` object (`old_tag`, `new_tag`, `new_sqlite_classes`, …). Cloudflare states "Once a Worker has been deployed with `exports`, subsequent deploys cannot return to the legacy `migrations` array." v1 therefore cannot manage this Worker. **[V]** — `alchemy@0.94.0 src/cloudflare/worker-metadata.ts:397-405`; https://developers.cloudflare.com/durable-objects/reference/durable-objects-migrations/ (updated 2026-09-28)
- Alchemy builds the map in three passes. Every namespace Cloudflare lists for the script stays a live entry with its observed storage backend. Classes hosted by current bindings are added as live entries. Renames, deletes and incoming transfers computed for this deploy are then applied as tombstones. New classes are always `sqlite`. **[V]** — `alchemy@b83 src/Cloudflare/Workers/WorkerProvider.ts:5567-5624` (`observedStorage`, `buildDurableObjectExports`)
- This Worker has no Alchemy tags. With no `alchemy:dos:` tag to map logical ids, the provider matches each declared binding to the live binding by binding name on a locally owned class, and reuses that class. For `TRIP_STORE` and `TripStore` that produces no new, renamed or deleted class. **[V]** — `alchemy@b83 src/Cloudflare/Workers/WorkerProvider.ts:3442-3451`, `:3653-3684`, `:3703-3747`; `src/Cloudflare/Workers/DurableObject.ts:1233-1262`
- Traced through that code with `name: "japan-trip-december-2026"`, binding `TRIP_STORE` and class `TripStore`, the adopting deploy would send `exports = { TripStore: { type: "durable-object", storage: "sqlite" } }`. That is the same map `wrangler.jsonc:16-18` sends today, with the same binding and no tombstones. **[V]** for the trace — `WorkerProvider.ts:3458-3490` (`TripStore` is in `currentDoClasses`, so it is not a delete candidate), `:3636-3646`, `:3688-3693`, `:5602-5608`. No adopting deploy was run, so the result is **[U]**. Settle it with `alchemy plan --adopt`, which is read-only, and its `durable object reconciliation {…}` log line (`WorkerProvider.ts:3750-3759`).
- Alchemy refuses adoption by default. `Worker.read` returns the existing script as `Unowned` when it lacks the three ownership tags, and the engine fails with `OwnedBySomeoneElse` unless the deploy runs with `--adopt` or `adopt(true)`. **[V]** — `alchemy@b83 src/Cloudflare/Workers/WorkerProvider.ts:1939-1948`, `:5219-5227`; `src/AdoptPolicy.ts:5-31`; https://alchemy.run/cli/adopting-resources
- The Worker name must be pinned. Without `name`, Alchemy derives a physical name from stack, stage and logical id, and would create a second Worker with an empty `TripStore` and its own `workers.dev` hostname. The existing Worker-level Access application would not cover that Worker. The in-Worker gate would still reject requests without a valid token, but Cloudflare serves prerendered pages from static assets without running the Worker. **[V]** — `alchemy@b83 src/Cloudflare/Workers/Worker.ts:517-521`; `src/PhysicalName.ts:13-30`; `src/server.ts:34-37`. The exposure on such a Worker is **[U]** because none was created.
- On the adopting deploy the declared `className` must equal the live class. A different `className` under the same binding name is treated as a rename (a `renamed` tombstone). A different binding name and class is treated as a new class plus a delete of the old one. **[V]** — `alchemy@b83 src/Cloudflare/Workers/WorkerProvider.ts:3475-3490`, `:3740-3747`; `src/Cloudflare/Workers/DurableObject.ts:1249-1255`
- Alchemy infers deletes from absence. Dropping the binding from `alchemy.run.ts` makes the class a delete candidate. Once the account's namespace list confirms it, Alchemy emits `{ type: "durable-object", state: "deleted" }`. With Wrangler a delete only happens when someone writes that tombstone by hand. **[V]** — `alchemy@b83 src/Cloudflare/Workers/WorkerProvider.ts:3459-3468`, `:3539-3590`, `:5612-5614`
- Cloudflare blocks the accidental case. It rejects a `deleted` tombstone for a class that the uploaded code still exports with `tombstone_delete_class_still_in_code`. Losing `TripStore` this way needs both the binding removed from the stack and the class export removed from `src/server.ts:12`. A namespace left undeclared fails with `orphaned_provisioned_namespace` and is not deleted. **[V]** — https://developers.cloudflare.com/durable-objects/reference/durable-objects-migrations/ (error table; updated 2026-09-28); PR #2135 body
- "There is no Trash for Durable Object namespaces deleted through `exports`." **[V]** — same Cloudflare page
- `alchemy destroy`, or removing the Worker resource from the program, calls `deleteScript({ force: true })` on the live script. That removes the Worker, and with it the namespace and all Trip data. **[V]** for the call — `alchemy@b83 src/Cloudflare/Workers/WorkerProvider.ts:845-871`, `:5389-5420`; https://alchemy.run/cli/destroy. I did not re-verify in Cloudflare's docs that deleting a script deletes its Durable Object storage, so that part is **[U]**.
- Running `alchemy dev` against the deployed stage is a third delete path, and it is specific to Alchemy. A resource that switches between live and local mode is planned as a replacement, and "the old instance is deleted with the provider of the mode that created it". `alchemy dev` defaults to a different stage (`dev_$USER`) for this reason, but `alchemy dev --stage <deployed stage>` or a shared `$ALCHEMY_STAGE` in `.env` reaches it. **[V]** — `alchemy@b83 src/ProviderMode.ts:15-19`; `src/Plan.ts:469-480`, `:775-778`; https://alchemy.run/environments/stages ("is a live ⇄ local replacement of that stage"). Not exercised, so **[U]** at runtime.
- `RemovalPolicy.retain()` on the Worker guards all three paths. The engine then never calls the provider's `delete` on destroy, on orphaning, or for the old generation of a replacement, and only drops the state row. Alchemy persists the policy on the state row at deploy time, and `destroy` and the orphan sweep read it from there, not from the code. **[V]** — `alchemy@b83 src/RemovalPolicy.ts:4-26`; `src/Apply.ts:1119-1120`, `:1987-1994`; https://alchemy.run/cli/destroy ("Retained resources")
- After adoption the script carries the tags `alchemy:stack:<stack>`, `alchemy:stage:<stage>`, `alchemy:id:<id>` and a packed `alchemy:dos:` tag. **[V]** — `alchemy@b83 src/Cloudflare/Workers/WorkerProvider.ts:1939-1943`, `:3761-3768`. Whether a later `wrangler deploy` keeps or clears them is **[U]**.

## 4. Cloudflare Access (Q4)

- Alchemy can manage the application and its policies. `Cloudflare.Access.Application` supports `self_hosted` apps with `destinations` of type `worker`, `preview_worker`, `all_workers` and `all_preview_workers`, inline `policies`, session duration and IdP settings. **[V]** — `alchemy@b83 src/Cloudflare/Access/Application.ts:58-72`, `:148-335`; `src/Cloudflare/Access/WorkerDestination.ts`
- Worker-level enrolment is a Worker prop. `access: { policies: […] }` creates a dedicated application named `<Worker>/Access`, and `access: <Application>` enrols the Worker into a shared one. Either way Alchemy pushes the Worker's `worker` destination, and `preview_worker` unless `previews: false`, onto the application. `Website.*` resources accept the same prop. **[V]** — `alchemy@b83 src/Cloudflare/Workers/Worker.ts:575-608`; `src/Cloudflare/Workers/WorkerAsyncBindings.ts:80-130`; https://alchemy.run/cloudflare/security/access
- The dedicated form would create a second application with a new AUD, which breaks `ACCESS_AUD` (`wrangler.jsonc:24`). The existing application can be taken over by id instead. `applicationId` "takes that application over" and keeps its `aud`, and a missing id fails with `DeclaredApplicationNotFound` without creating anything. This arrived in `beta.82`. **[V]** — `alchemy@b83 src/Cloudflare/Access/Application.ts:100-108`, `:153-160`, `:436-443`; `gh release view v2.0.0-beta.82` ("Adopt Applications by id", #1848)
- The application's `aud` is an output attribute, so `ACCESS_AUD` could be read from it and stop being a copied literal. **[V]** — `alchemy@b83 src/Cloudflare/Access/Application.ts:340-345`
- Removing an `Access.Application` from the program deletes the application in Cloudflare unless it is retained. **[V]** — `alchemy@b83 src/Cloudflare/Access/Application.ts:832-838`; `src/RemovalPolicy.ts:4-12`
- For `policies` on an application the source says "If omitted, the application's live policies are left as they are. Pass `[]` to detach them". Inline and reusable policies cannot be mixed on one application. Adopting with `policies` omitted is therefore the first step that changes no policy. **[V]** — `alchemy@b83 src/Cloudflare/Access/Application.ts:279-300`
- Two things are not established. One is the shape of the existing application, created from the dashboard's Worker Access tab, as the API reports it. The other is what else the first reconcile of an adopted application would change (session duration, destinations, cookie settings). Both are **[U]**. Settle them by reading the app with `GET /accounts/{id}/access/apps/{app_id}` and comparing it with `alchemy plan`.
- Alchemy has a dev simulation, `dev.access: { aud?, identity? }` on the Worker. Its implementation file first appears in commit `67022d6` (2026-08-16, "protect Workers with Access", #1228). The option does nothing on deploy. **[V]** — `alchemy@b83 src/Cloudflare/Workers/Worker.ts:972-998`; `gh api "repos/alchemy-run/alchemy/commits?path=packages/alchemy/src/Cloudflare/Workers/WorkerAccess.ts"`
- The simulation does not populate the native `ctx.access`. Alchemy lowers the config into a JSON env binding named `ALCHEMY_DEV_ACCESS`. The only reader is `resolveAccessContext`, used by Alchemy's Effect-native Worker runtime (`Cloudflare.Access.Context`), which falls back to that binding when `ctx.access` is undefined. **[V]** — `alchemy@b83 src/Cloudflare/Workers/RuntimeBindings.ts:296-302`, `:329`; `src/Cloudflare/Workers/WorkerAccess.ts:146-177`; `src/Cloudflare/Workers/WorkerRuntime.ts:73`; `src/Cloudflare/Access/Context.ts:31-35`
- workerd has a native mechanism (`accessBlobHeader`, `accessBindingService`), and the runtime package's config type declares both fields, but nothing in `@alchemy.run/cloudflare-runtime` or `alchemy` sets them. **[V]** — `cf-runtime@b83 src/core/workerd/Config.ts:105-106`; `rg accessBlobHeader|accessBindingService` over both tarballs' `src/` finds only those two lines and the generated `config.capnp.ts` docs
- The docs page says that with `dev.access` "`ctx.access` carries the given `aud`". For a plain `fetch(request, env, ctx)` Worker like `src/server.ts` the source says otherwise. `ctx.access` stays undefined and the data is on `env.ALCHEMY_DEV_ACCESS`. **[V]** for the code path and **[U]** at runtime. Settle it by logging `ctx.access` and `env.ALCHEMY_DEV_ACCESS` under `alchemy dev`. https://alchemy.run/cloudflare/security/access ("Test locally")

## 11. What it buys (Q11)

- Alchemy would replace one 36-line `wrangler.jsonc`, `wrangler deploy`, `wrangler types`, and a manually created Worker-level Access application with one policy. **[V]** — `wrangler.jsonc`; `package.json:10-11`; `docs/research/cloudflare-access.md:111`

- Several of Alchemy's gains do not apply here. There is one Worker and one same-Worker Durable Object, so there is no multi-resource wiring. There is no CI, so there are no CI previews. There is one cloud and one developer.

Stop if any of them is non-empty or if the plan shows a create. There is nothing to roll back. This step makes read-only API calls.
- **Step 7, first deploy, which changes the live Worker.** Command: `alchemy deploy --adopt --stage prod`. It uploads a new bundle built by Alchemy's plugin with the same `exports` map, adds the ownership and `alchemy:dos:` tags, turns observability on unless it is set, adds `new_module_registry` to the flags, and records the `retain` removal policy. To roll back, check out the last Wrangler commit and run `pnpm run deploy`. The Worker never left the `exports` flow, so Wrangler can deploy it again. What Wrangler does with the leftover tags and observability setting is **[U]**.
- **Step 8, Access as code, optional, which changes the Access application.** Changed: `alchemy.run.ts`. Add `Cloudflare.Access.Application("Access", { applicationId: "<existing id>", type: "self_hosted" }).pipe(RemovalPolicy.retain())` with `policies` omitted at first so the live policy is left alone, pass it as `access` on the Worker, and read `ACCESS_AUD` from `app.aud`. Add `policies` in a later deploy. Commands: `alchemy plan --stage prod`, then `alchemy deploy --stage prod`. To roll back, remove the resource, which is retained so the application stays, and correct any changed setting in the dashboard.
- **Step 9, cleanup.** Deleted: `wrangler.jsonc`. Changed: `AGENTS.md` (Cloudflare bindings, commands), `README.md`, `docs/agents/*` where they mention Wrangler, a new ADR superseding 0004, and `~/.claude` notes that say this project uses Wrangler. This step does not touch the live Worker.

### Open risks

- The prerender blocker in step 4 has no option that keeps today's behaviour. **[V]** for the code path, **[U]** for the failure.
- The gate needs a dev-only identity path that ADR 0004 rejected, keyed on a binding name that no docs page describes. **[V]**
- v2 is a beta with breaking changes in four of its last six releases, and the one feature this Worker depends on (`exports`) shipped on 2026-10-12. **[V]**
- Three data loss paths do not exist with Wrangler: `destroy`, removing the resource, and `dev` on the deployed stage. Each ends in `deleteScript({ force: true })`. `retain()` covers them once a deploy has recorded it. **[V]**
- A missing or wrong `name` makes Alchemy create a second Worker outside the Access application. The only signal is that the plan shows a create where an adoption was expected. **[V]** — `alchemy@b83 src/AdoptPolicy.ts:17-21`
- Adoption changes script settings beyond the code: tags, observability and an extra compatibility flag. **[V]**; the effect of the flag is **[U]**.
- Effect version alignment under the exact pin is **[U]** until a lockfile resolves it.
- These were never exercised here and are all **[U]**: an adopting deploy of an `exports`-managed Worker, `alchemy dev` with TanStack Start under Vite+, top-level `cloudflare:workers` `env` in dev, asset and `_headers` parity, and adoption of the existing Access application. Each needs a scratch Worker, not this one.

### Verdict

- Do not adopt Alchemy for this app now. The full switch is blocked by prerendering and requires the dev-only gate code that ADR 0004 rejected. The partial shapes B and C keep `wrangler.jsonc` and add a beta dependency, a state store and new delete paths. In return they replace `wrangler deploy` or manage one Access application.
- The Durable Object is not the obstacle. From `beta.82` the adopting deploy sends the same `exports` map Wrangler sends, and Cloudflare refuses the accidental delete while the class is still in the code.
- Revisit when three things hold: v2 has a stable release, its Vite build passes bindings and an Access simulation to the build-time preview, and local development can populate the native `ctx.access`. Check them in the source before starting, and rehearse steps 6 and 7 on a scratch Worker that Wrangler deployed with an `exports`-declared SQLite class.
