## 1. Does the Vite plugin read `cloudflare.config.ts`? (Q1)

Without it, the plugin takes the `getValidatedWranglerConfigPath` branch. **[V]** — `node_modules/@cloudflare/vite-plugin/dist/index.d.mts:102-135`, `dist/index.mjs:65674-65690`, `:16305`

This repo passes only `viteEnvironment: { name: 'ssr' }`, so none of those trip. **[V]** — `dist/index.mjs:65674-65679`, `:65825-65855`, `:57074`; `vite.config.ts:79`

## 2. Durable Object: binding vs `ctx.exports` (Q2)

- `cf migrate` always emits a required item per DO binding; it converts `durable_objects.bindings[{name,class_name}]` to `bindings.durableObject({ worker: <this Worker's name>, exportName })`. Docs step: "Review each generated binding. In `bindings.durableObject({ worker, exportName })`, `worker` is the name of the Worker that defines the class". The doc's own example keeps the self-named binding. **[V]** — https://developers.cloudflare.com/cf/wrangler/migrate/#durable-objects (updated 2026-09-29)
- `worker` is required on `bindings.durableObject` (no "self" shorthand). **[V]** — `node_modules/.pnpm/@cloudflare+config@0.22.0/node_modules/@cloudflare/config/dist/public-DFY8wDEh.d.mts:1321-1335`
- A self-named binding is treated as local: 1.62.0 converts it to `{ name, class_name, script_name: worker }`; Wrangler classifies `script_name === config.name` as a local binding; plugin 2.0 beta uses the same self-named `type: "durable-object", worker: worker.config.name` shape for its own internal DO. **[V]** — 1.62.0 `dist/index.mjs:57323-57328`; `wrangler-dist/cli.js:198553-198563`; 2.0 beta `dist/index.mjs:83898-83902`
- Docs: "`ctx.exports.Counter` — Accesses a class exported by the same Worker without an `env` binding"; "Live Durable Object exports become typed properties on `ctx.exports`. A Worker does not need an `env` binding to call its own class." The example sets `compatibilityFlags: ["enable_ctx_exports"]`. **[V]** — https://developers.cloudflare.com/cf/projects/cloudflare-config/#distinguish-exports-from-bindings (updated 2026-09-29)
- `enable_ctx_exports` is default-on from compatibility date 2025-11-17; this Worker's date is 2025-09-02, so `ctx.exports` needs the flag or a date bump. **[V]** — https://developers.cloudflare.com/workers/configuration/compatibility-flags/ (updated 2026-09-18); https://developers.cloudflare.com/workers/runtime-apis/context/ (updated 2026-09-28: "you must use the `enable_ctx_exports` compatibility flag"); `wrangler.jsonc:4`
- The DO is reached from TanStack server functions through the module-scoped `env` import (`env.TRIP_STORE.getByName('phillip', { locationHint: 'apac-ne' })`), where no `ctx` exists; `ctx` exists only in `src/server.ts`'s `fetch`. Moving to `ctx.exports` means threading the namespace from `src/server.ts` (e.g. via request context) or using the module export `exports` from `cloudflare:workers`. **[V]** — `src/trip/trip-store.server.ts:1,23`, `src/server.ts:35-45`
- Runtime types declare `export const exports: Cloudflare.Exports` on `cloudflare:workers` alongside `env`. **[V]** — `worker-configuration.d.ts:14351-14352`. Runtime availability of that module-level export is not documented on the Context page. **[U]**
- Typing: with `worker` given as a string, the inferred binding type is untyped `DurableObjectNamespace` (generic defaults to `undefined`), not `DurableObjectNamespace<TripStore>` as `wrangler types` emits today; `ctx.exports.TripStore` is typed only if `entrypoint` is a module imported `with { type: "cf-worker" }` (string `entrypoint` → `DefaultModule`). **[V]** — `public-DFY8wDEh.d.mts:300-310`, `:410-420`, `:841-854`; `worker-configuration.d.ts:9,533`; https://developers.cloudflare.com/cf/wrangler/migrate/#finish-the-project ("With a string path, `Env` binding types are still inferred, but the types of your Worker module exports are not"). Whether `callTripStore`'s `DurableObjectStub<TripStore>` parameter then fails `tsc`: **[U]**
- `exports` vs legacy `migrations`: `cloudflare.config.ts` has no `migrations` field; `worker.exports` "replaces the ordered `migrations` history". This repo already deploys with `exports` (`wrangler.jsonc:16-18`), and `cf migrate` carried it over as `TripStore: exports.durableObject({ storage: "sqlite" })`, matching the live class. **[V]** — https://developers.cloudflare.com/cf/wrangler/reference/#convert-durable-object-migrations (updated 2026-09-29); `cloudflare.config.ts:44-48`
- Lifecycle risk is in the declaration, not the tool: renames, deletes and transfers must be declared as tombstones (`state: "renamed" | "deleted" | "transferred"`); "Use `cf deploy`, rather than a version upload, for a version that creates, deletes, renames, or transfers a Durable Object class. You cannot roll back a Durable Object lifecycle change". Keeping `name: "japan-trip-december-2026"` and the live `TripStore` sqlite entry makes no lifecycle change. **[V]** — same reference page; https://developers.cloudflare.com/cf/projects/cloudflare-config/#manage-durable-object-lifecycle; `cloudflare.config.ts:27,45`. No first-hand `cf deploy` of an existing `exports`-managed namespace was run. **[U]**
- Local DO state moves: plugin 1.62.0 persists to `.wrangler/state/v3` (current data in `.wrangler/state/v3/do/japan-trip-december-2026-TripStore`); plugin 2.0 beta persists to `.cloudflare/state/v3`; `cf`'s global `--persist-to` default is `~/.config/cloudflare/state`. Local Schedule data would not carry over without copying. **[V]** — 1.62.0 `dist/index.mjs:89016-89019`; 2.0 beta `dist/index.mjs:83632-83635`; `cf migrate --help`; `ls .wrangler/state/v3/do`

## 3. Access dev simulation (`ctx.access` locally) (Q3)

- The gate's dev path needs, together: no `Cf-Access-Jwt-Assertion` header, `ACCESS_DEV_SIMULATION` truthy in the Worker's env, and a `ctx.access` whose `aud` equals `ACCESS_AUD` and whose `getIdentity()` returns the allowed email. Without `ctx.access`, a header-less request is refused 403. **[V]** — `src/access/AccessGate.ts:42-50`, `:132-162`; `src/server.ts:37`
- `cloudflare.config.ts` has no `access` field (WorkerConfig, bindings and exports have no Access entry); the `cf` field-mapping table has no `access` row; `cf migrate` drops it with a required TODO. **[V]** — `public-DFY8wDEh.d.mts:819-920`; https://developers.cloudflare.com/cf/wrangler/reference/#configuration-fields (updated 2026-09-29); `cloudflare.config.ts:19-22`
- Plugin 1.62.0 feeds `access: entryWorkerConfig?.access?.dev` to Miniflare in dev, but under `newConfig` the config comes from `convertToWranglerConfig`, which never emits `access` and the `config` customiser is rejected, so there is no way to inject it. Preview under `cfBuildOutput` also rebuilds config via `convertToWranglerConfig` (no `access`). **[V]** — `dist/index.mjs:89046-89053`, `:57074-57091`, `:65678`, `:58638-58647`
- Plugin 2.0 beta passes no `access` option to Miniflare at all (router worker options have none). **[V]** — 2.0 beta `dist/index.mjs:83730-83740`; grep for `access` finds only the Wrangler-config validator
- `wrangler.config.ts` (`wrangler/experimental-config`) `dev` options have no Access setting either. **[V]** — `node_modules/wrangler/wrangler-dist/experimental-config.d.mts:1-77`
- No `cf` docs page mentions Access dev simulation or `ctx.access`. **[V]** — grep of https://developers.cloudflare.com/cf/projects/, /cf/projects/cloudflare-config/, /cf/projects/config-explorer/, /cf/wrangler/, /cf/wrangler/migrate/, /cf/wrangler/reference/ (index.md, updated 2026-09-29/30)
- Prerendering depends on it: `vite.config.ts` prerenders "through the local preview, whose Access dev simulation passes the gate". Under the new config there is no simulation in preview, so prerender requests would get 403. **[V]** for the dependency — `vite.config.ts:81-91`; **[U]** for the build failure (not run)

## 4. Type generation (Q4)

- `cf workers types` ("Generate types from cloudflare.config.ts", option `--include-runtime`, default true) writes the fixed path `.cloudflare/types/index.d.ts`; the Vite plugin (1.62.0 with `newConfig`, and 2.0 beta) writes the same file on dev/build. **[V]** — `cf workers types --help`; `node_modules/cf/dist/command-DzHL5LKI.mjs`; https://developers.cloudflare.com/cf/projects/#generate-types (updated 2026-09-30); 1.62.0 `dist/index.mjs:65812-65840`
- The generated header is `Cloudflare.Env extends InferEnv<worker>` plus `GlobalProps { mainModule: InferMainModule; durableNamespaces: InferDurableNamespaces }`, then runtime types; i.e. structurally the same shape as `worker-configuration.d.ts`. **[V]** — `@cloudflare/config/dist/index.mjs:716-733`; `worker-configuration.d.ts:2-18`
- Differences from `wrangler types`: env types come only from `cloudflare.config.ts`, not `.dev.vars` (today `ACCESS_DEV_SIMULATION: string` comes from `.dev.vars`); `bindings.text("…")` values type as their literal; DO binding typing per §2. **[V]** — `@cloudflare/config/dist/index.mjs:716-733`; `public-DFY8wDEh.d.mts:300-320`; `worker-configuration.d.ts:5-9`. The gate reads env through `ConfigProvider.fromUnknown(env)`, so it does not need these static types. **[V]** — `src/server.ts:18`
- `tsconfig.json` includes `**/*.ts` with no `.cloudflare/types` entry; `cf` scaffolds `include: ["src", "cloudflare.config.ts", ".cloudflare/types"]`. Keeping both `worker-configuration.d.ts` and `.cloudflare/types/index.d.ts` would declare runtime types twice. **[V]** for the configs — `tsconfig.json:4`, `node_modules/cf/dist/init-BGcAIvV7.mjs`; **[U]** for resulting `tsc` errors

## 5. `.dev.vars` and local env (Q5)

- Docs: "Local secrets in `.dev.vars` keep working under `cf dev`"; `cf migrate` "never reads secret files" and lists them as info. **[V]** — https://developers.cloudflare.com/cf/wrangler/ (updated 2026-09-30); https://developers.cloudflare.com/cf/wrangler/migrate/#secrets
- Plugin 2.0 beta loads `.dev.vars.<mode>` then `.dev.vars` from Vite's `envDir`, but uses those values only to fill bindings declared `bindings.secret()`; `bindings.text()` values stay as configured, and undeclared keys are not added to `env`. So `ACCESS_DEV_SIMULATION` would not reach the Worker, and `.dev.vars` would no longer override `ACCESS_TEAM_DOMAIN` / `ACCESS_AUD`. **[V]** — 2.0 beta `dist/index.mjs:48301-48346`, `:83388-83417`, `:79018`; `.dev.vars` keys: `ACCESS_TEAM_DOMAIN`, `ACCESS_AUD`, `ACCESS_DEV_SIMULATION`
- Plugin 1.62.0 (with or without `newConfig`) still goes through Wrangler's `getVarsForDev`, which merges all `.dev.vars` keys when no `secrets` block exists. **[V]** — `wrangler-dist/cli.js:185491-185531`; 1.62.0 `dist/index.mjs:79863-79875`. Exact dev-path call under `newConfig`: **[U]**
- Declaring a key as `bindings.secret()` makes it a deploy-time secret too (`secrets.required`); `cf deploy` uploads secrets only via `--secrets-file`. **[V]** — 1.62.0 `dist/index.mjs:57524`; https://developers.cloudflare.com/cf/projects/#deploy

## 6. Deploy (Q6)

- `cf deploy` builds (framework command, or `cf-vite build` with forced Build Output), validates `.cloudflare/output/v0/`, uploads a Worker Version and deploys it; `--prebuilt` deploys existing Build Output (must pass the recorded `--mode`, `production` for Vite builds); `--dry-run` uploads nothing. It does not consume `dist/server/wrangler.json`. **[V]** — https://developers.cloudflare.com/cf/projects/#deploy, #deploy-a-prebuilt-build (updated 2026-09-30); `cf deploy --help`; 1.62.0 `dist/index.mjs:90717-90718`
- `cf` does not run `package.json` scripts, so `vp build` (and the `tanstackStart` prerender + `checkPrerenderedHtml` it runs through `vite.config.ts`) only runs if Vite itself is launched with this config; extra steps must be chained by hand. **[V]** — https://developers.cloudflare.com/cf/projects/#how-cf-runs-your-project
- `workers_dev` → `worker.workersDev`, `preview_urls` → `worker.previewUrls` (both migrated: `true` / `false`); `cf deploy` applies triggers, and `cf workers triggers deploy` applies "the `workers.dev` setting" alone. **[V]** — https://developers.cloudflare.com/cf/wrangler/reference/#configuration-fields; https://developers.cloudflare.com/cf/projects/#deploy-triggers; `cloudflare.config.ts:33-34`
- Still needs Wrangler after migrating: `wrangler tail`, single `wrangler secret put`. **[V]** — https://developers.cloudflare.com/cf/wrangler/reference/#commands-not-yet-supported
- `cf` uses its own login (`cf auth login` or `CLOUDFLARE_API_TOKEN`), not Wrangler's. **[V]** — https://developers.cloudflare.com/cf/wrangler/#use-cf-alongside-a-wrangler-project

## Implications for this repo

- **Q1 / overall:** `wrangler.jsonc` cannot be removed while (a) `vite.config.ts` uses plugin 1.62.0 without `experimental.newConfig`, (b) `deploy`/`cf-typegen` call Wrangler, and (c) Access dev simulation is needed (only `wrangler.jsonc` can express it). Full migration requires `@cloudflare/vite-plugin@beta` (2.0, beta), `cf` scripts, and a way for `cf` to launch Vite here (`vite` bin absent under Vite+). Options: stay on Wrangler (chosen, ADR 0004); run dual (the generated config alongside `wrangler.jsonc`, inert); or full switch after the Access blocker is resolved.
- **TODO durable_objects.bindings.0:** keep the self-named `TRIP_STORE` binding (works locally and on deploy, minimal code change, loses `DurableObjectNamespace<TripStore>` typing), or drop it for `ctx.exports.TripStore` / `cloudflare:workers` `exports` (needs `enable_ctx_exports` or compat date ≥ 2025-11-17, a `cf-worker` entrypoint import for typing, and a route from `src/server.ts` to server functions). No blocker.
- **TODO exports.TripStore:** the generated `TripStore: exports.durableObject({ storage: "sqlite" })` matches the deployed namespace; keep the name and class unchanged and deploy with `cf deploy`, not a version upload. Local DO data path changes (`.wrangler/state` → `.cloudflare/state`).
- **TODO access:** **blocker for a full switch.** Neither `cloudflare.config.ts`, plugin 1.62.0 `newConfig`, plugin 2.0 beta, nor `wrangler.config.ts` can provide `ctx.access` locally, and 2.0 beta also drops undeclared `.dev.vars` keys (`ACCESS_DEV_SIMULATION`). Without a replacement, local dev and the preview-based prerender would be refused by the gate. Options: keep Wrangler/1.62.0 for dev and build; change the gate's dev identity mechanism (ADR 0002 and `docs/research/cloudflare-access.md` §5 decision); or wait for upstream support.
- **`.dev.vars`:** fine under 1.62.0; under 2.0 beta only `bindings.secret()` keys are read, which changes override semantics for the Access vars.
- **Types:** `cf workers types` → `.cloudflare/types/index.d.ts` replaces `wrangler types` → `worker-configuration.d.ts`; needs `tsconfig.json`, `.gitignore`, lint/fmt ignore and AGENTS.md updates, and must not coexist with the old file.
