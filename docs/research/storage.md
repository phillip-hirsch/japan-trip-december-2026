## 3. Migration tooling

- D1: `wrangler d1 migrations create|list|apply <database_name> --local|--remote`; plain `.sql` files in `migrations/` (configurable via `migrations_dir`/`migrations_pattern`), tracked in `d1_migrations` (configurable). "If applying a migration results in an error, this migration will be rolled back, and the previous successful migration will remain applied." Docs recommend addressing by database name, not binding. `wrangler d1 execute` and `wrangler d1 export` exist. **[V]** — https://developers.cloudflare.com/d1/reference/migrations/ (updated 2026-06-08); https://developers.cloudflare.com/workers/wrangler/commands/d1/
- D1 remote migrations are a separate step from `wrangler deploy`, so schema and code do not ship atomically. **[V]** (follows from the above)
- DO SQLite: no Cloudflare CLI for table schema. Two layers: (a) class lifecycle via `exports`; (b) table schema in app code — "Use `blockConcurrencyWhile()` in the constructor to run migrations"; "`PRAGMA user_version` is not supported by Durable Objects SQLite storage", use a tracking table. If the `blockConcurrencyWhile` callback throws, "the object will be terminated and reset". `sql.exec()` cannot run `BEGIN`/`SAVEPOINT`; use `ctx.storage.transaction()/transactionSync()`. **[V]** — https://developers.cloudflare.com/durable-objects/best-practices/rules-of-durable-objects/; https://developers.cloudflare.com/durable-objects/api/state/ (updated 2026-09-30); https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/ (updated 2026-09-21)
- `@effect/sql-sqlite-do`'s `SqliteMigrator` is exactly this pattern with a tracking table (`effect_sql_migrations`), so migrations ship with the code and run lazily per object. **[V-src]**
- Cloudflare's own framing: "With SQLite in Durable Objects, you may also need to build some of your own database tooling that comes out-of-the-box with D1"; "By design, Durable Objects are accessed with Workers-only." **[V]** — https://developers.cloudflare.com/durable-objects/best-practices/access-durable-objects-storage/

## 5. Store characteristics

- Workers KV: "eventually-consistent"; "changes may take up to 60 seconds or more to be visible" elsewhere; "not ideal for applications where you need support for atomic operations or where values must be read and written in a single transaction". **[V]** — https://developers.cloudflare.com/kv/concepts/how-kv-works/ (updated 2026-04-21). The 1 write/sec per-key figure is **[U]** (not on that page's summary).
- D1: `batch()` — "Batched statements are SQL transactions. If a statement in the sequence fails ... it aborts or rolls back the entire sequence." Non-session queries always go to the primary. **[V]** — https://developers.cloudflare.com/d1/worker-api/d1-database/ (updated 2026-06-22)
- D1 limits: 500 MB/db and **50 queries per Worker invocation** on Free (10 GB / 1000 on Paid); 100 bound params/query. Time Travel: 7 days Free, 30 days Paid. Location hints: `wnam, enam, weur, eeur, apac, oc` only; default placement near where the DB was created. **[V]** — https://developers.cloudflare.com/d1/platform/limits/; https://developers.cloudflare.com/d1/reference/time-travel/; https://developers.cloudflare.com/d1/configuration/data-location/
- DO SQLite: available on Workers Free ("Only Durable Objects with SQLite storage backend are available"); Free: 5M rows read/day, 100k rows written/day, 5 GB total. PITR restores "any point in time in the past 30 days" (`getCurrentBookmark`, `getBookmarkForTime`, `onNextSessionRestoreBookmark`); PITR "not supported in local development". Location hints include `apac-ne` (Northeast Asia-Pacific); "Durable Objects do not currently change locations after they are created. Only the first call to `get()` ... will respect the hint"; hints are best effort. **[V]** — https://developers.cloudflare.com/durable-objects/platform/pricing/ (updated 2026-09-30); sqlite-storage-api; https://developers.cloudflare.com/durable-objects/reference/data-location/ (updated 2026-06-26)
- DO is single-threaded per object with input/output gates, so phone and desktop writes to the same object are serialised. **[U]** as a claim about lost-update prevention in this app (platform behaviour is documented; correctness still depends on the app's mutation design).

- Recommendation (A: D1; B: Durable Object SQLite). Resolved in favour of B. A's case for D1 rested on (a) not being able to reach the npm registry, so it treated @effect/sql-d1 as unverified and proposed a hand-rolled Effect.tryPromise wrapper, and (b) assuming DO migrations must be hand-rolled. - Import path of @effect/sql-sqlite-do (A: source imports `effect/unstable/sql`, from unpinned GitHub main; B: `effect/sql`). Resolved: the published rc.118 tarball imports `effect/sql/*` exclusively (grep on package/src/*.ts). A was looking at a stale/unpinned main.

## Recommendation

Use a single Durable Object with SQLite storage (e.g. class `TripStore`, addressed via `env.TRIP_STORE.getByName('phillip')`), accessed through `@effect/sql-sqlite-do@4.0.0-rc.118` pinned in lockstep with `effect@4.0.0-rc.118`.

Why: (1) It is the only Cloudflare store where Effect v4's `effect/sql` toolkit works unchanged — `withTransaction` with real rollback, `SqliteMigrator`, `SqlModel`/`SqlSchema` — which matters because forking an itinerary into a Schedule and reordering activities are multi-row atomic writes. On D1 the Effect driver turns `withTransaction` into a defect and the Effect Migrator cannot run, forcing two parallel systems (`D1Client.batch` for atomicity, Wrangler `.sql` files for schema) and a discipline of "never call withTransaction" that a future contributor or agent will eventually break. (2) Schema migrations ship atomically with the code (run in the constructor under `blockConcurrencyWhile`), removing the deploy-ordering hazard D1 has. (3) Everything stays behind Cloudflare Access with no second identity system — DOs are Workers-only. (4) It works on Workers Free with 30-day PITR, avoids D1 Free's 50-queries-per-invocation cap, and can be pinned near Japan with `locationHint: 'apac-ne'` (D1 only offers `apac`). (5) Single-threaded per-object execution serialises phone/desktop writes, and the same object can later host WebSockets for live sync.

Accepted costs: a custom `src/server.ts` entrypoint that re-exports the TanStack Start handler and the DO class (`main: "src/server.ts"`); `exports: { TripStore: { type: "durable-object", storage: "sqlite" } }` in wrangler.jsonc (never combine with `migrations`; deploy with `wrangler deploy`, not `versions upload`); migrations written as Effect/SQL strings rather than CLI-managed `.sql` files; less ad-hoc tooling than `wrangler d1 execute`; a failing constructor migration resets the object until fixed (wrap in try/catch and fail requests explicitly); add `@cloudflare/workers-types@5.20260930.1` as a direct devDependency so the driver's `storage` option type does not degrade to `any`; each RPC result must be serialisable.

Runner-up: D1 with `D1Client.batch` for every multi-row write and `wrangler d1 migrations` for schema — choose it only if you value D1's managed dashboard/CLI/export tooling over Effect-native transactions. Reject Workers KV (eventually consistent, no transactions) and Convex (public endpoint requiring Clerk, beta Convex Auth, or a custom JWT bridge; no Japan region; Effect v4 support only via `@confect/core@next`).

## Decisions surfaced

- Store: confirm Durable Object SQLite over D1. The trade is Effect-native transactions + code-shipped migrations (DO) versus Cloudflare-managed tooling like `wrangler d1 execute`, dashboard console and export (D1). Both hold a few hundred rows trivially.
- DO placement is permanent: pass `locationHint: 'apac-ne'` on first creation to optimise for the phone in Japan in December (at the cost of higher latency for desktop planning beforehand), or omit it and let it land near wherever the first request originates. Hints are best-effort.
- Object topology: one singleton DO for Phillip (simplest, one migration target) versus one DO per Schedule/fork (isolation, but routing and per-object migrations). This shapes the RPC API and how itinerary forks are modelled.
- Offline and multi-device requirements: do Schedule edits need to work offline on a flaky connection in Japan and sync later, and should simultaneous phone/desktop edits detect conflicts rather than last-write-wins? Neither server store gives you this; it would require a client-side store and a versioned-mutation sync protocol, and it is easier to design into the DO API now (e.g. WebSocket + version numbers) than to retrofit.
- Dependency policy for Effect v4 RC: adopt `@effect/sql-sqlite-do` and accept pinning it in exact lockstep with `effect` (paths moved between rc.117 and rc.118), versus writing a thin app-owned Effect wrapper over `ctx.storage.sql` to insulate from RC churn. Recommendation is to adopt the driver; the alternative is a legitimate reliability-first choice.
- Cloudflare plan: Workers Free suffices for DO SQLite (30-day PITR included). If you keep D1 as a fallback, Free means 7-day Time Travel and 50 queries per invocation.
- Auth boundary: rely solely on Cloudflare Access (email OTP) in front of the Worker, but decide whether the Worker should also validate `Cf-Access-Jwt-Assertion` on server functions as defence in depth. Choosing Convex would instead force a second identity system (Clerk / beta Convex Auth / custom JWT bridge) — this is the main reason to rule it out.
